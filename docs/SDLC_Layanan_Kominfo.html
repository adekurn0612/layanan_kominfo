1. Ringkasan dan Tujuan

Portal Layanan Kominfo menyediakan katalog layanan teknologi informasi, formulir pengajuan yang dikonfigurasi dari data layanan, pembuatan tiket ber-UUID, pelacakan status, QR code tiket, serta pengelolaan layanan dan tiket oleh administrator.

Tujuan SDLC ini adalah memastikan perubahan sistem direncanakan, dibangun, diuji, dirilis, dan dipelihara secara terkendali. Dokumen ini juga menjadi acuan pembagian tanggung jawab dan bukti minimum sebelum perubahan masuk produksi.

Prinsip pengembangan

  • Berbasis kebutuhan layanan dan pengalaman pemohon.
  • Validasi server-side sebagai sumber kebenaran.
  • Least privilege untuk akses administrasi.
  • Perubahan kecil, dapat ditelusuri, dan dapat dipulihkan.
  • Data pemohon dan dokumen lampiran diperlakukan sebagai data terbatas.

2. Ruang Lingkup dan Aktor

2.1 Dalam ruang lingkup

  • Halaman publik: beranda, katalog layanan, kategori, detail layanan, berita placeholder, dan cek tiket.
  • Autentikasi: registrasi, login, logout, throttling login/registrasi, serta dashboard.
  • Pengajuan layanan oleh pengguna terautentikasi menggunakan field dinamis dari database.
  • Tiket: UUID, status submitted, in_review, in_progress, completed, dan rejected.
  • Tindak lanjut tiket berupa komentar atau file, dengan visibilitas publik/internal.
  • Administrasi organisasi, pengguna, role, permission, kategori, layanan, field, requirement, tiket, dan tindak lanjut.

2.2 Di luar atau perlu dikonfirmasi

  • Notifikasi email/SMS/WhatsApp, SLA escalation otomatis, dan integrasi sistem eksternal belum terbukti pada source yang dipindai.
  • Rencana backup, monitoring produksi, pemulihan bencana, dan persetujuan operasional perlu ditetapkan oleh pemilik sistem.
  • Detail klasifikasi data, retensi, dasar hukum, dan petugas privasi perlu dikonfirmasi.

4. Arsitektur dan Desain

Aplikasi mengikuti pola MVC Laravel: route meneruskan request ke controller, controller memuat model/service, validasi dilakukan oleh validator, policy membatasi akses, dan view menyajikan antarmuka web. Vite menangani asset frontend.

4.1 Komponen utama

KomponenTanggung jawab
Public webKatalog layanan, detail requirement, login/register, cek tiket, QR.
Application layerPengajuan layanan, normalisasi form, pembuatan tiket, status, tindak lanjut.
AuthorizationRole/permission dan policy organisasi, user, service, ticket, serta modul admin.
Data layerUsers, organizations, roles, permissions, service categories/services/fields/requirements, tickets, follow-ups.
File storageLampiran pengajuan dan file tindak lanjut disimpan pada storage aplikasi dengan metadata file.

4.2 Model data ringkas

Organisasi memiliki user dan dapat terkait dengan tiket. Kategori memiliki banyak service. Service memiliki field dinamis dan requirement. Service menghasilkan banyak ticket. Ticket memiliki follow-up yang dibuat oleh user. UUID ticket bersifat unik sebagai identifier pelacakan publik.

Definition of Done

  • Kebutuhan dan acceptance criteria terhubung dengan implementasi.
  • Validasi dan authorization sudah diuji pada jalur sukses dan gagal.
  • Migration dapat dijalankan pada environment bersih dan tidak merusak data yang ada.
  • Test, lint, dan build lulus; dokumentasi perubahan diperbarui.
  • Reviewer dan pemilik produk menyetujui; risiko rilis memiliki mitigasi.

6. Keamanan dan Privasi

  • Gunakan akun dengan role minimal; audit perubahan role/permission dan tindakan admin.
  • Jangan menaruh secret di repository; gunakan environment variable dan secret manager produksi.
  • Validasi tipe, ukuran, MIME, nama, dan lokasi penyimpanan file; cegah file upload menjadi executable atau dapat diakses tanpa authorization.
  • Batasi endpoint lookup agar tidak menjadi sarana enumerasi UUID atau kebocoran data. Tampilkan hanya follow-up yang public kepada pemohon.
  • Gunakan HTTPS, cookie aman, CSRF protection, throttling, dan session invalidation saat logout/perubahan kredensial.
  • Redaksi data pribadi dan isi form_data dari log aplikasi. Tetapkan retensi dan prosedur penghapusan.
  • Lakukan dependency audit PHP dan npm, patch berkala, serta review kerentanan sebelum rilis.

Kontrol yang perlu dibuktikan pada deployment produksi: header keamanan, konfigurasi debug off, backup terenkripsi, restore drill, rotasi secret, dan pemantauan akses file.

8. Deployment dan Operasi

8.1 Environment

EnvironmentTujuanAturan
LocalPengembangan individual.Data dummy; tidak memakai secret produksi.
StagingIntegrasi dan UAT.Konfigurasi menyerupai produksi; data disanitasi.
ProductionLayanan pengguna nyata.Approval rilis, backup, monitoring, HTTPS, debug off.

8.2 Checklist rilis

  1. Review perubahan dan hasil test.
  2. Backup database dan storage; verifikasi backup dapat dibaca.
  3. Install dependency dengan mode production dan build asset.
  4. Set environment, cache konfigurasi/route sesuai prosedur, lalu jalankan migration yang disetujui.
  5. Smoke test: login, katalog, pengajuan, lookup UUID, QR, admin ticket, follow-up.
  6. Pantau log dan error rate; dokumentasikan hasil serta keputusan rollback.

8.3 Rollback

Rollback harus memiliki trigger yang jelas: migrasi gagal, error kritis, kebocoran data, atau alur pengajuan tidak dapat digunakan. Kembalikan versi aplikasi, pulihkan database hanya bila diperlukan dan disetujui, verifikasi smoke test, lalu buat incident record.

9. Pemeliharaan dan Manajemen Perubahan

Semua perubahan dicatat sebagai issue/change request dengan alasan bisnis, dampak data, risiko keamanan, acceptance criteria, owner, dan rencana rollback. Perubahan pada migration, policy, validator, route, dan storage dikategorikan berdampak tinggi dan memerlukan regression test.

11. Kriteria Penerimaan dan Tindak Lanjut

11.1 Kriteria penerimaan baseline

  • Pengunjung dapat menemukan layanan aktif dan requirement-nya.
  • Pemohon yang belum login diarahkan ke login saat hendak mengajukan.
  • Field wajib dari konfigurasi service divalidasi dan error ditampilkan.
  • Pengajuan valid menghasilkan UUID unik, status submitted, dan halaman lookup.
  • User tanpa permission tidak dapat membuka modul admin.
  • Admin dapat memperbarui status dan menambahkan tindak lanjut sesuai validasi.
  • Test suite, lint, dan build asset lulus pada pipeline rilis.

11.2 Tindak lanjut prioritas

  1. Tambahkan feature test untuk transisi status dan batasan visibilitas follow-up publik/internal.
  2. Tambahkan test keamanan untuk download file, rate limit lookup, dan sanitasi data/log.
  3. Tetapkan target SLA operasional, RTO/RPO, retensi data, dan owner incident.
  4. Siapkan pipeline CI yang menjalankan php artisan test, Pint check, dependency audit, dan npm run build.
  5. Lakukan UAT bersama pemilik layanan dengan data dan skenario yang disetujui.
